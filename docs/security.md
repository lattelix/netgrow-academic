# Безопасность NetGrow

## 1. Модель угроз (сводно, STRIDE)

| Категория | Угроза в контексте NetGrow | Контроль |
| --- | --- | --- |
| Spoofing (подмена личности) | Посетитель выбирает чужую роль | Демо-вход намеренно позволяет выбирать синтетические аккаунты, включая администратора. Это не проверка личности. После входа роль берётся из серверной сессии, а не из тела бизнес-запроса |
| Tampering (изменение данных) | Изменение чужого проекта/заявки/задачи через прямой вызов API | Проверка владения в `src/lib/domain/authorization.ts` перед каждой мутацией |
| Repudiation (отказ от действий) | Организатор отрицает, что принимал решение по заявке | `activity_log` фиксирует `actor_id`, действие и время для каждой мутации |
| Information disclosure (утечка данных) | Просмотр чужого профиля/заявок через подбор идентификатора | Каталог требует сессии и доступен всем вошедшим ролям. Полный список пользователей доступен только администратору, отдельный профиль только владельцу и администратору; заявки фильтруются по роли и владению |
| Denial of Service | Не актуально для локального демо-стенда без внешнего трафика | Вне периметра демонстрационной версии, см. раздел «Production-рекомендации» |
| Elevation of Privilege | Участник вызывает административный эндпоинт | Каждый маршрут проверяет роль через `canManageReferenceData`/`canViewAnalytics`/др. до выполнения действия |

## 2. Матрица авторизации

| Действие | Участник | Организатор (свой проект) | Организатор (чужой проект) | Администратор |
| --- | --- | --- | --- | --- |
| Просмотр каталога проектов | ✅ | ✅ | ✅ | ✅ |
| Подать заявку | ✅ | ❌ | ❌ | ❌ |
| Отозвать свою заявку | ✅ (своя) | ❌ | ❌ | ✅ |
| Создать/редактировать проект | ❌ | ✅ | ❌ | ✅ |
| Одобрить/отклонить заявку | ❌ | ✅ | ❌ | ✅ |
| Создать/обновить задачу | ❌ | ✅ | ❌ | ✅ |
| Изменить статус своей задачи | ✅ (исполнитель) | ✅ | ❌ | ✅ |
| Просмотр аналитики | ❌ | ✅ | ❌ | ✅ (все проекты) |
| Чтение списка пользователей | ❌ | ❌ | ❌ | ✅ |
| Чтение отдельного профиля через API пользователей | Только свой | Только свой | Только свой | ✅ |
| Чтение журнала действий | ❌ | Сущности своего проекта | ❌ | Все записи |
| Чтение командных событий | Команды с членством | Команды своего проекта | ❌ | Все команды |
| Управление сменами/компетенциями/ролями | ❌ | ❌ | ❌ | ✅ |

Матрица реализована как явные, независимо тестируемые функции в
`src/lib/domain/authorization.ts` (покрыты `authorization.test.ts`), а не разбросана по
условиям внутри обработчиков — это снижает риск забыть проверку в новом маршруте.

Общие события видны всем вошедшим ролям; фильтр смены только сужает доступный набор.
Для организатора аналитика считает участников с заявкой или членством в его проектах,
без двойного подсчёта. Число организаторов в этой сводке относится только к владельцам
его проектов; при отсутствии проектов все показатели пустые или нулевые. Администратор
получает общесистемные показатели. Журнал организатора включает действия любых авторов
над сущностями его проектов, но не глобальные записи профилей и справочников.

`/api/demo-accounts` публичен специально для выбора учебного аккаунта. Он возвращает
ограниченный набор синтетических полей, а не полный профиль. Эти ограничения доступа
нельзя считать защитой закрытых данных: любой посетитель может выбрать демо-администратора.

## 3. Реализованные технические меры

- **Централизованная валидация**: все тела запросов проходят через схемы Zod
  (`src/lib/validation/schemas.ts`) до обращения к базе — некорректные данные
  отклоняются с кодом `400` и структурированным списком ошибок.
- **Формат ожидаемых ошибок**: `src/lib/api/respond.ts` возвращает ошибки проверки входа,
  доступа и конфликтов со структурой `{ error: { code, message } }`. Непредвиденные ошибки
  БД, включая сбой аудита, прерывают запрос и обрабатываются Next.js как серверный сбой;
  единый JSON-формат для всех таких ошибок не гарантирован.
- **Cookie сессии**: `HttpOnly`, `SameSite=Lax`, `Secure` включается автоматически при
  `NODE_ENV=production` (`src/lib/auth/session.ts`). `HttpOnly` исключает доступ к cookie
  из клиентского JavaScript (защита от XSS-кражи сессии).
- **SQL-инъекции**: все запросы выполняются через параметризованные запросы `pg`
  (`$1..$N`-плейсхолдеры). Динамические SQL-фрагменты формируются из фиксированных
  условий; значения из запросов пользователей передаются только как параметры.
- **Ограниченное логирование**: `activity_log` хранит идентификаторы и служебные метаданные,
  в том числе названия учебных проектов, задач и событий, но не содержимое профиля
  и сообщений заявок. Автоматического распознавания персональных данных нет: не вводите
  реальные или закрытые сведения даже в названия объектов.
- **Атомарность аудита**: бизнес-изменение и запись журнала используют один transaction
  client через `withTransaction`. Сбой журнала откатывает изменение данных. Cookie входа
  и выхода не являются частью SQL-транзакции; запись журнала выполняется перед их изменением.
- **Изоляция данных окружений**: адрес PostgreSQL задаётся переменной окружения
  `DATABASE_URL` (тесты используют отдельную `TEST_DATABASE_URL`, e2e — отдельную базу
  `netgrow_e2e`), что позволяет держать данные разработки, тестов и e2e-прогонов в разных
  базах без риска перезаписать чужие данные.

## 4. Резервное копирование (демонстрационный контур)

Для локального демо-стенда резервное копирование не требуется — состояние полностью
восстанавливается командой `ALLOW_DB_RESET=1 pnpm db:reset` (см. `demo-script.md`, раздел
«Восстановление после сбоя»). Это осознанная замена традиционного бэкапа: детерминированный
сид данных гарантированно воспроизводим и не хранит ничего, что нельзя пересоздать. Команда
требует явного `ALLOW_DB_RESET=1` и никогда не выполняется автоматически при сборке или
развёртывании.

## 5. Production-рекомендации (не реализованы в демо-версии)

Следующие меры выходят за рамки локального учебного стенда, но обязательны при переносе
архитектуры в продуктивную эксплуатацию:

1. **Полноценная аутентификация**: замена демо-выбора аккаунта на пароль/OAuth с хешированием
   (например, argon2) и защитой от перебора (rate limiting на `/api/session`).
2. **HTTPS обязателен**: включить `Secure` и `HSTS`; демо-режим допускает HTTP только для
   `localhost`.
3. **CSRF-защита** для мутирующих запросов, если сессия используется из сторонних доменов
   (в демо-версии не требуется — same-origin fetch из собственного клиента).
4. **Резервное копирование** управляемой PostgreSQL (например, точечное восстановление и
   снапшоты у хостинг-провайдера БД, такого как Neon) и репликация для продуктивной нагрузки.
5. **Ограничение частоты запросов** (rate limiting) на мутирующие эндпоинты для защиты от
   автоматизированного злоупотребления.
6. **Аудит доступа к `activity_log`** — в продуктиве доступ к журналу действий следует
   дополнительно ограничить и хранить дольше нормативного срока хранения персональных данных.
7. **Секреты и конфигурация** — вынести в переменные окружения/секрет-менеджер, что уже
   заложено архитектурно через `DATABASE_URL` и аналогичные переменные.
